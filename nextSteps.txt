Where we started

Originally, the interesting observation was:

“If you show an AI the confidence number it previously gave, it changes whether it wants its answer checked.”

That was surprising because nothing about the answer changed. For GPT, showing confidence made it verify much less; for Claude, it often made it verify more.

But that was mostly an observation. We didn’t know why.

Then came Checkpoint A.

What Checkpoint A actually told us

Checkpoint A asked a more important question:

Suppose the AI says “99% confident.” Is that number actually everything the AI knows about whether the answer is risky?

And the answer looked like no, at least behaviorally.

The clearest example was GPT. There were lots of answers where GPT had given the exact same confidence, 99%. Yet when the confidence number was hidden, GPT treated some of those answers as “this should be checked” and others as “this is safe.”

Even more importantly, the ones GPT naturally wanted checked were actually wrong much more often.

So in layman’s terms:

GPT’s single confidence number was throwing away some useful nuance.

Not necessarily secret neurons or “the model knows it’s wrong.” It could simply be that when GPT gets another look at the problem during the verification stage, it notices something it didn’t encode into the original percentage.

That is the core Checkpoint A clue.

At the same time, Checkpoint A prevented us from telling a fake story. For GPT, much of the original bad outcome from showing confidence was simply because GPT was overconfident and then faithfully followed that overly optimistic number. So we stopped saying things like “showing confidence definitely suppresses a superior internal signal.” That was not established.

Then Study 1 answered a different question

Study 1 asked:

Is the number itself actually causing the later decision?

So we froze the exact same question and exact same answer and literally changed only the displayed confidence.

GPT’s result was extreme.

At \(L=10\):

show 89% → essentially always CHECK;
show 91% → essentially never CHECK.

At \(L=20\):

show 94% → essentially always CHECK;
show 96% → essentially never CHECK.

And the repeat study showed this wasn’t randomness. Rerunning the exact same GPT prompt changed the decision only about 2–3% of the time; changing the confidence across the threshold changed it around 99% of the time.

So we now have a clean causal fact:

For GPT in this setup, the displayed confidence number can almost completely control the verification decision.

Claude responds too, but much less mechanically. Its tiny near-threshold effect did not survive reruns cleanly, although moving from very low to very high displayed confidence still had a substantial effect.

That’s a real result.

But—and this is where Claude’s critique was important—it is not yet a crazy discovery.

Why Claude says the current result is somewhat obvious

Imagine I tell you:

“This answer has a 91% chance of being correct. Checking costs 1 point. Using a wrong answer costs 10 points.”

There is a mathematically correct decision:

don’t check.

If I instead say 89%, the math says:

check.

So if GPT behaves exactly that way, a reviewer can reasonably say:

“Congratulations, GPT understood the instructions and did the arithmetic.”

And actually GPT is arguably behaving correctly given what we told it.

So the paper cannot be:

“GPT is bad because it obeys confidence too much.”

That would be conceptually weak.

Claude’s better framing is to stop blaming the model and start questioning the system design.

The designer chose to compress all uncertainty into one number, then fed that number back into the model and essentially told it to base oversight on that number.

The question becomes:

What useful information might the system lose when it does that?

That is much more interesting.

This is the “bridge to Checkpoint A”

This is the key connection.

Checkpoint A tells us:

When the confidence number is hidden, the model’s natural CHECK/USE decision sometimes contains useful information that the confidence number itself does not contain.

Study 1 tells us:

When the number is explicitly shown, especially for GPT, that number can almost completely control the final CHECK/USE decision.

Put those together:

What happens to that extra useful information when we feed the confidence number back in?

That is the bridge.

Here’s the simplest possible example.

Suppose we show 99% confidence to every question.

Now the displayed confidence contains zero information about which particular question is wrong, because every question gets the exact same number.

GPT at 99% basically says:

“Use them all.”

So its final decision distinguishes almost none of the questions.

Claude at 99% still checks many of them.

The important question is which ones Claude checks.

If Claude’s checked answers are disproportionately the actually wrong ones, then Claude is still using useful question-specific evidence despite seeing the same 99% score everywhere.

If not, then Claude is just generally more cautious.

That’s the analysis we have not run yet.

And it could be the most important analysis so far.

So is what we have right now “good”?

Yes, but in a specific sense.

We now have a very clean exploratory causal finding.

Study 1 passed its own gate: the GPT effect is huge, stable under repetition, and caused by changing only the displayed confidence.

I would describe the current package as:

Too strong to dismiss as a fluke, but not deep enough yet to be the ICLR story.

Right now you have something I would be happy with as a strong workshop contribution.

For ICLR, we need to answer the next layer.

What the strong ICLR story could become

The strongest version I currently see is something like this:

AI systems increasingly need to decide which of their own outputs deserve extra scrutiny. Confidence scores are an obvious way to make that decision. But a confidence score is only a compressed summary of uncertainty. We find that once the score is fed back into the model as a control input, it can dramatically reshape the verification policy and, in some models, potentially crowd out answer-specific information that was useful for identifying errors. We measure how much useful information survives, explain where that information comes from, and design routing policies that preserve it and catch more errors at the same oversight budget.

That is narratively strong because it has a clean progression:

AI needs selective oversight
→ confidence seems like the obvious routing signal
→ confidence is only a summary
→ feeding that summary back changes behavior
→ maybe it replaces richer answer-specific judgment
→ measure what survives
→ figure out where it comes from
→ design a better router.

That feels like one paper.

Not six disconnected experiments.

What would make it a very strong ICLR paper

I would now think about the project in roughly five steps.

Prove the “evidence retention” result.
On the Study-1 data we already have, hold displayed confidence fixed and ask whether VERIFY vs USE still predicts actual wrongness. If Claude retains useful error discrimination and GPT loses most of it, that is potentially the conceptual centerpiece. This costs nothing.
Rule out the boring explanation for Checkpoint A.
Ask for a second confidence estimate. Maybe the “extra information” in hidden verification is simply the benefit of looking at the question twice. If a second confidence sample explains everything, we should say so. If it does not, the deeper story survives.
Remove the arithmetic crutch.
Run a qualitative-stakes experiment with no exact cost formula or crisp numerical threshold. If GPT still lets the displayed score strongly dominate—and especially if useful answer-specific discrimination drops—then the result is no longer just “GPT did arithmetic.”
Confirm and generalize.
Freeze a fresh experiment on unseen questions, ideally add one open-weight model and one non-MCQ task such as math. The Master Plan already treats fresh prospective confirmation and modest generalization as the core path after the exploratory pilot.
Show a practical payoff.
At the same number of allowed checks, compare:
raw confidence, calibrated confidence, natural verification judgment, repeated assessment, and combinations. If a combined router catches more real mistakes for the same checking budget, the paper ends with something designers can actually use.

That last part matters a lot narratively.

Otherwise the paper ends:

“Here is a weird behavior.”

Much better is:

“Here is the failure mode, here is why it happens, and here is a better way to allocate oversight.”

Where interpretability fits now

Much later.

Claude was right here too.

We do not need activation steering or probes just to make this respectable.

If the behavioral story becomes strong:

explicit score dominates;
useful answer-specific evidence disappears or weakens;
this survives second-confidence controls;
survives qualitative stakes;
generalizes;
better router recovers performance;

that could already be a strong paper.

Interpretability then becomes the high-ceiling question:

What internal signal is being used when confidence is hidden, and does displaying confidence reduce its influence on the final action?

That would be exciting.

But we shouldn't do it just because “ICLR likes mechanistic work.”

The Master Plan itself says the mechanistic contribution only earns its place if the behavioral continuity and stronger baselines survive first.

The current project landscape, in plain English

I’d divide where we are into four boxes.

What we know:
GPT’s displayed confidence can causally and almost deterministically control verification in our numerical-cost setup. That survives rerun noise. Claude is less score-dominated. Checkpoint A also showed natural verification contains information beyond one verbal-confidence report.

What we strongly suspect but haven’t shown:
When GPT becomes score-dominated, some useful answer-specific discrimination may stop influencing the decision.

What could kill the deeper story:
Maybe Claude’s residual checking is just blanket caution. Maybe asking for confidence a second time completely explains the hidden-policy advantage. Maybe GPT only acts this way because we literally gave it an arithmetic threshold.

What would turn it into the strong paper:
Show that useful answer-specific evidence really gets reduced by explicit-score conditioning, survives boring-explanation controls, replicates prospectively and across another setting, and can be exploited to build a better routing policy.

The simplest version of the whole paper

If everything works, I think the elevator pitch eventually becomes:

A confidence score is not the same thing as everything an AI knows about whether its answer is risky. When we feed that score back into the model to control whether its answer gets checked, some models let the score dominate the decision. We study what useful information is lost, why, and how to route verification better.

That is much stronger than:

“Changing 89% to 91% changes GPT’s action.”

The 89→91 result is now the instrument that lets us study the deeper phenomenon, not the phenomenon we ultimately want the paper to be remembered for.
