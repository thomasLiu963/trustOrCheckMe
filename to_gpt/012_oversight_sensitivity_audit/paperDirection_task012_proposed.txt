======================================================================
1. THE FINAL PAPER IN ONE PARAGRAPH
======================================================================

Large language models increasingly operate inside systems that cannot afford
to independently verify every output. They must decide when to spend an
external verification resource: a human reviewer, a stronger model, retrieval,
additional compute, a specialized checker, or an executable test suite.
Confidence is a natural control signal for such routing decisions, but its
causal role is unclear when the signal is fed back into an adaptive model:
does changing the confidence shown to the model alter which outputs receive
scrutiny, or mainly how often scrutiny is requested?

D1 isolates this question with a fixed-output counterfactual intervention.
After an LLM generates an answer, the answer is frozen. We then vary only the
confidence value displayed back to the model before it decides whether to use
the output directly or request independent verification.

On a fresh preregistered MMLU-Pro study, changing displayed confidence from
0.70 to 0.99 shifts verification coverage by 50.2 percentage points for GPT
and 35.4 points for Claude. A preregistered richer model that allows
score-dependent reprioritization provides essentially no held-out predictive
gain over the shared-prioritization baseline.

We then repeat the intervention in a more realistic executable setting:
frozen code solutions from LiveCodeBench can be sent to an independent hidden
test suite. GPT again shows a large 38.8-point confidence-driven coverage
shift. Claude, however, remains near-always VERIFY_FIRST and moves only
4.9 points, revealing a model/task boundary condition rather than a universal
law.

Those same coverage shifts change error leakage
(P(incorrect AND USE_UNVERIFIED | displayed q)) on an unchanged incorrect-
output population. POST_HOC_SYSTEMS_REANALYSIS: MMLU GPT 2.0% → 13.8%
(+11.8 pp); MMLU Claude 0.0% → 3.8% (+3.8 pp); code GPT 10.8% → 32.9%
(+22.0 pp); code Claude 0.0% → 1.4% (+1.4 pp). The manipulated 0.70–0.99
range overlaps naturally reported q1 (GPT MMLU 92%; GPT code 71%). The
normalized-loss cost of the wrong operating point depends on λ.

The final conclusion is therefore behavioral and systems-oriented:
counterfactual confidence is a high-leverage metadata actuator for oversight
intensity and escaped-error leakage. Leverage is model- and task-dependent.
Changing the scalar alone is not established as a reliable way to improve
allocation quality, and the constant overwrite is not a calibration or
natural-q1-drift intervention.

======================================================================
3. THE REAL SYSTEMS PROBLEM
======================================================================

The motivating problem is resource-bounded verification.

Suppose an AI system produces many outputs but can only verify a fraction of
them.

It faces two distinct questions:

A. COVERAGE / BUDGET
    How many outputs should receive verification?

B. ALLOCATION
    Which outputs should receive that verification budget?

These are not the same problem.

A routing controller can be excellent at setting the verification rate while
poorly targeting the risky cases.

The final paper should be motivated around adaptive systems where confidence
or uncertainty enters a routing/controller decision, including:

- model cascades;
- human escalation;
- adaptive retrieval;
- test-time compute allocation;
- safety delegation;
- tool use;
- executable testing / code verification.

The paper should NOT claim that ordinary monotonic recalibration changes
ranking. That is false as a framing target and unnecessary.

The live empirical question is narrower:

    When a confidence-like scalar is inserted into an ADAPTIVE model/controller
    that can condition on the full item, does changing that scalar merely move
    the amount of resource use, or does it materially alter which items are
    prioritized?

That question is not tautological because the LLM can react item-by-item to
the scalar, the content, difficulty, apparent mismatch with its own judgment,
or other contextual features.

======================================================================
4. THE CORE CAUSAL DESIGN
======================================================================

Natural confidence is confounded with item difficulty.

If hard questions naturally produce:
- lower confidence;
- more verification;

then observing a confidence-verification correlation is not enough.

D1 therefore intervenes on displayed confidence while holding the underlying
output fixed.

For each item:

1. model produces an answer/program;
2. that output is frozen;
3. the model has a confidence-style estimate q1;
4. Stage 3 presents a routing prompt;
5. only the displayed confidence is manipulated;
6. the model chooses USE_UNVERIFIED or VERIFY_FIRST.

The question and frozen output do not change across score conditions.

This isolates the displayed scalar as a causal input into routing behavior.

This fixed-output counterfactual intervention is one of the strongest and most
defensible contributions of the paper.

5. WHAT IS AND IS NOT NOVEL
======================================================================

DO NOT CLAIM NOVELTY FOR:

- confidence affecting abstention;
- confidence affecting escalation;
- threshold policies;
- risk-coverage curves;
- the distinction between coverage and ranking;
- uncertainty-guided routing in general.

Recent work already occupies much of that space.

The potentially novel package is:

1. FIXED-OUTPUT COUNTERFACTUAL CONFIDENCE INTERVENTION

   Same question/problem.
   Same frozen output.
   Different displayed confidence.

2. CONFIDENCE AS AN INPUT TO AN ADAPTIVE ROUTING POLICY

   The scalar is placed inside the model's context before the routing action.
   The model is not externally thresholded by us.

3. QUANTITY-VERSUS-ALLOCATION QUESTION

   We do not stop at:
       “does confidence change escalation?”

   We ask:
       “what part of the routing policy changes when the scalar changes?”

4. PROSPECTIVE EVIDENCE ACROSS TWO VERY DIFFERENT SETTINGS

   - academic QA with idealized independent verification;
   - executable code with a real hidden-test verifier.

5. MODEL/TASK BOUNDARY CONDITION

   The intervention is powerful in GPT across both settings, powerful in
   Claude on MMLU, but weak in Claude on hard code because the routing action
   is near the VERIFY ceiling.

The novelty is therefore the causal behavioral characterization of an
adaptive verification-routing policy, not the discovery of thresholding.

9. CHECKPOINT A — CALIBRATION VS COVERAGE VS ALLOCATION
======================================================================

The original workshop interpretation risked saying:

    showing confidence makes GPT worse at verification.

Checkpoint A showed why that was too strong.

GPT was overconfident.

If the model faithfully follows an overconfident scalar, then visible
confidence can move it toward a lower-verification operating point.

That can leave more wrong answers unchecked without requiring a claim that
the model lost useful item-specific information.

This establishes an important three-way distinction:

CALIBRATION
    Are probability values numerically meaningful?

COVERAGE CONTROL
    Does the signal change how much verification occurs?

ALLOCATION QUALITY
    At a matched verification budget, are the right outputs selected?

This conceptual separation remains central to the final paper.

15. TASK 010 — WHAT IT CHANGED
======================================================================

Task 010 did NOT overturn the Task-009 coverage result.

It changed the interpretation of the ranking claim.

Key sensitivity result:

- the Task-009 H2 detector had a high detection floor;
- GPT reached high power only for a large structured ranking rewrite;
- Claude did not reach 80% power even at the largest tested structured effect;
- the detector had no useful power for generic item-condition noise.

Therefore:

    Task 009 supports “little held-out gain for the preregistered richer model.”

It does NOT support:

    “the ranking is globally invariant.”

Task 010 also found:

- shared-model AUROC predictions matched the direction, but not fully the

- three-repeat latent propensity modeling was too weak/overshrunk to support a

- post-hoc q1/mismatch features predicted VERIFY beyond the frozen baseline;
- matched-budget routing showed a GPT-specific gain at some budgets but no

The paper-facing consequence:

    retire exact ranking-invariance language.

Task 010 belongs mainly in:
- limitations;
- robustness/sensitivity appendix;
- claim-discipline discussion.

It should not become a main-paper result.

28. WHY THIS RESULT IS STILL INTERESTING
======================================================================

A hostile selective-prediction reviewer may say:

    “Of course moving a threshold changes coverage.”

The answer:

We do NOT externally move a threshold on a fixed score.

We alter the scalar INSIDE an adaptive LLM's context.

The model can:
- react to apparent score-content mismatch;
- condition differently on item difficulty;
- change which features it attends to;
- use the score as a reason to reassess routing item-by-item.

Therefore a purely coverage-like response is an empirical behavior, not a
mathematical necessity.

The code result strengthens this argument because VERIFY_FIRST now requests a
real operation.

And the Claude code boundary shows the effect is not merely hardwired to
always appear: when the routing policy is already near the VERIFY ceiling, the
same manipulation has little leverage.

======================================================================
29. THE SYSTEMS DESIGN IMPLICATION
======================================================================

The practical message should be:

    A confidence scalar can be an effective actuator for setting how much
    independent verification a model requests, but actuator strength depends
    on the operating regime.

    Controlling the amount of verification is not the same as learning which
    outputs have the highest value of verification.

Therefore system builders should separately evaluate:

A. RESPONSE / CONTROL
    Can the signal move verification coverage?

B. ALLOCATION
    At a matched budget, does the policy target high-value/error-prone cases?

C. SATURATION
    Is the policy already near always-verify or never-verify, making the signal
    ineffective?

This three-part framing may now be better than the old
“coverage vs ranking” framing alone.

On frozen LiveCodeBench programs with actual hidden-test verification, GPT
again shifts by 38.8pp, while Claude stays near the VERIFY ceiling and moves

CONTRIBUTION 4 — ALLOCATION IS DISTINCT FROM CONTROL

Across both prospective studies, preregistered score-specific prioritization

32. ABSTRACT-LEVEL NARRATIVE
======================================================================

Draft direction, not final wording:

Large language models increasingly decide when their outputs require additional
scrutiny, yet it is unclear what confidence feedback actually controls inside
an adaptive verification-routing policy. We isolate this question with a
fixed-output counterfactual intervention: after a model produces an answer, we
freeze the output and vary only the confidence value displayed before the model
chooses whether to request independent verification. On a preregistered study
of 500 unseen MMLU-Pro questions, this intervention changes verification
coverage by 50.2 percentage points for GPT and 35.4 points for Claude. A
preregistered score-specific prioritization model provides essentially no
additional held-out predictive benefit over the simpler baseline. We then
generalize the intervention to executable code, where VERIFY_FIRST requests an
actual hidden test suite. GPT again shows a large 38.8-point coverage shift,
whereas Claude remains near an always-verify ceiling and moves only 4.9 points.
These results show that displayed confidence can be a powerful causal actuator
of verification quantity, but its leverage depends on the routing regime and
should not be conflated with allocation quality.

40. LIMITATIONS
======================================================================

1. CLOSED MODELS
   Internal mechanisms, system prompts, and post-training policies are not
   observable.

2. BEHAVIORAL, NOT MECHANISTIC
   The intervention identifies the causal effect of displayed confidence on
   behavior, not the internal path producing it.

3. MODEL/TASK HETEROGENEITY
   Claude's code behavior differs sharply from its MMLU behavior.

4. ACTION SATURATION
   Near-always VERIFY policies make responsiveness/allocation hard to identify.

5. NO GLOBAL RANKING-INVARIANCE RESULT
   The H2 test has limited sensitivity to smaller/generic reranking.

6. SIMPLE ROUTERS DO NOT SHOW A ROBUST CROSS-MODEL WIN
   D1 characterizes control behavior; it does not solve optimal routing.

7. MANIPULATED DISPLAYED CONFIDENCE IS ARTIFICIAL
   This is a deliberate causal instrument, not necessarily a deployment
   distribution.

8. VERIFIER SEMANTICS DIFFER BY TASK
   MMLU uses an idealized independent verifier;
   code uses real hidden tests.

9. TEMPORAL MODEL DEPENDENCE
   Deployed closed-model behavior may change across versions.
